# GeoLineAI specification

GeoLineAI: **Evidence-grounded assistance for geophysical review.**

This is the product specification for GeoLineAI. It defines the user journey, the invariants, the HTTP surface, the dataset, and the acceptance criteria. Where this document and the code disagree, the code is wrong or this document needs an explicit amendment.

## Scope

GeoLineAI implements exactly one user journey:

1. Choose one of three fixed sample readings.
2. Inspect its measured values, deterministic quality checks, and supporting evidence.
3. Ask a question about those checks.
4. Receive an evidence-grounded explanation, a withheld-answer explanation, an unanswerable result, or a clear unavailable result.
5. Explicitly choose and save a human verdict for that one reading.
6. Reload the reading and see its saved verdict and review history.

GeoLineAI is a conventional local application: a Go backend, a React frontend, and one SQLite database. It has no agent orchestration, tool protocols, plugins, independently deployed services, registries, code generation beyond the Go-to-TypeScript type generation, or extension points for hypothetical future requirements.

Out of scope: a survey browser, line selection, filters, sorting, bulk selection or bulk review, progress dashboards, plots and charts, repeat-group browsing, investigation, handover drafting, undo, export, uploads, a general import interface, accounts, roles, login, collaboration, and multi-user conflict handling. None of these have routes, controls, or hidden placeholder screens.

## Identity

- Product and repository name: `GeoLineAI`.
- Go module path and executable: `geolineai`.
- Frontend package name: `frontend`.
- Agent and contributor instructions: `CLAUDE.md` and `CODING_STANDARDS.md` at the repository root.
- Visual identity: the favicon and palette of the author's website (see [User interface](#user-interface)).

## Ownership of decisions

| Owner | Decides |
| --- | --- |
| Deterministic code | Parsing, validation, units, calculations, criterion results, the advisory, counts, persistence, and every saved reason. |
| Models | Only the wording of an explanation drawn from supplied sources, and judgments of whether each sentence is supported and whether it tells a verdict. |
| Human reviewer | Every verdict (Pass, Fail, or Unreviewed), each by an explicit Save. |

Models never calculate measurements, choose an advisory, save a verdict, or edit the review record.

## Dataset

GeoLineAI ships one synthetic DCIP survey line, `data/line-1.csv`, generated by `scripts/generate-line/`. The dataset is synthetic: a SimPEG 2D DC and IP forward model of one conductive, chargeable body in a resistive background, followed by a seeded field-conditions step that adds noise, error estimates, contact resistance, and defects. Defects come only from the generator's documented, seeded rules applied across the whole line. No row is edited by hand, and no row is edited to create a scenario. Re-running the generator with the same seed reproduces the file byte for byte. Setup and verification never run the generator; the committed CSV is the input.

Constraints the code imposes on the line, which the generator respects:

- `line_id` is `line-1`, the only member of the closed line vocabulary.
- 40 electrodes, `line-1-e01` to `line-1-e40`, on a straight line.
- Dipole-dipole array with a = 1 and n from 1 to 8 (268 distinct geometries).
- Ten decay gates at the fixed gate centres defined in code.
- The CSV has the 30 columns the importer expects.

The criterion limits are domain rules defined in code and are not tuned to the data. The generator was designed with those limits in mind, so any gap between clean and defective values is by construction, and the documentation says so rather than presenting it as discovered evidence.

The whole line is imported. The scenario picker restricts what the screen shows; it never restricts the data available to calculations or evidence construction. Repeat groups, electrodes, decay samples, and the rest of the line stay available to the calculations and explanations.

### Scenarios

`data/scenarios.json` lists exactly three scenarios, each with a label and a stable source identity: the source file name and the row number the importer records, which is the physical line of the CSV with the header as line 1. Selection rules, applied to the computed results of the imported line, taking the first qualifying row in file order and requiring three distinct readings:

1. **Passing reading:** the first reading whose deterministic advisory is Pass.
2. **Violated criterion:** the first reading with a Violated result on a measurement criterion (any criterion other than an import issue).
3. **Disagreeing repeats:** the first reading whose only unresolved result is a Review of repeat agreement: its repeats disagree, and the repeat comparison is the one reason it needs review. With the first two, the three scenarios cover all three advisory values.

Each reading stores the row number the importer recorded, and each import stores the file's path. `geolineai scenarios`, which `scripts/setup.sh` runs after every setup, resolves the manifest against the database and fails clearly when a scenario's row is missing or matches more than one reading, as it does when a file was imported twice. The server loads the manifest at start and resolves the same identities to internal reading IDs on each `GET /api/scenarios`. Internal IDs are never assumed to survive reseeding.

## Human review and persistence

- Only an explicit human Save changes a verdict.
- A save targets exactly one existing reading. A request with zero or several targets is rejected; there is no hidden bulk-write capability.
- Reading identifiers are validated, and the verdict vocabulary is closed: `pass`, `fail`, `unreviewed`.
- The verdict and its history entry are written atomically in one transaction.
- Review history is append-only. Database triggers refuse updates and deletes of history entries and actions.
- The server builds the reason saved with Pass and Fail from the reading's stored evaluation. Unreviewed saves no reason. Neither the client nor a model authors a saved reason.
- Reading detail carries `would_save_reasons`: the exact reason a save of Pass or of Fail would record, built by the same server code. The page shows it beside the verdict selector before Save, so the reviewer reads the reason before committing to it.
- Saving the verdict a reading already has creates no action.
- History shows, for the selected reading, each verdict transition, its time, and its saved reason.
- The recorded reviewer is the fixed string `reviewer`.
- There is no undo. A reviewer may save another verdict, which appends a new entry. There is no in-app reset.

GeoLineAI is a local, single-reviewer application. It has no authorization model, and the absence of an operation in the UI is not authorization.

## AI-assisted explanations

The explanation pipeline keeps three separate stages:

1. A text writer generates an explanation from a closed, numbered set of supplied sources.
2. Deterministic checks inspect every generated sentence and its citations.
3. A judgment model rates each sentence for support by its cited sources and for whether it tells a verdict, against fixed thresholds.

Sources are built from the selected reading, its relevant line context, the domain rules, and documentation passages quoted verbatim. Models receive only this closed source set.

Rules:

- Every sentence must cite at least one existing source. Numbers, identifiers, and criterion names in a sentence must appear in its cited sources. Sensitive wording is allowed only when a cited source uses it.
- An answer is shown only when every sentence passes the deterministic checks and the judgment thresholds.
- If any sentence fails, the whole answer is withheld. The response shows the problems and the available sources, not the rejected text.
- Generated answers are never persisted and never sent back to a model as a source.
- There is no provider switching, streaming, chat memory, conversation storage, or runtime fake-model mode. Scripted models exist only in tests.

### Outcome contract

`POST /api/readings/:id/explanations` returns HTTP 200 with one of four outcomes:

| Outcome | Meaning |
| --- | --- |
| `shown` | Every sentence passed; the answer and its sources are shown. |
| `withheld` | At least one sentence failed; problems and sources are shown, the answer text is not. |
| `unanswerable` | The writer validly reported that the sources cannot answer the question. |
| `unavailable` | No answer could be obtained. A `reason` field says why: `no_key` (the server has no provider key), `provider_error` (the provider failed after the configured retries), or `invalid_response` (malformed JSON, a missing required field such as `answerable`, a wrong type, or an out-of-range or missing judgment probability). |

An omitted `answerable` field is `invalid_response`, never a valid refusal. Every outcome includes the sources built for the question. A question that is empty or too long is a 400 `validation_error`. No outcome writes review state.

### Accuracy and configuration identity

The Ask panel always shows **Accuracy not measured for this configuration.**, whatever the answer state. No accuracy figure is claimed for GeoLineAI.

A configuration fingerprint covers the model identifiers, temperature, judgment thresholds, sentence and question limits, system prompt text, judgment questions, and documentation passages. `/_/health` reports it. The timeout and retry settings are operational and are deliberately excluded. Changes to source construction, the response schema, or the deterministic checks also require an evaluation review even though the fingerprint does not detect them. Regression tests establish application behavior; they do not establish the real-world accuracy of generated explanations.

### Citations

Every `[Sn]` in an answer links to its source card on the same page. A documentation source's card shows the full passage, verbatim from the repository document it cites, with the document path and section as a caption. A test enforces that each passage still appears verbatim in its document and that the section anchor exists. The server does not serve documentation files.

## User interface

One page titled **GeoLineAI** with:

1. A three-item scenario picker.
2. The selected reading's identity, relevant measured values, deterministic advisory, and per-criterion results.
3. Expandable supporting facts, repeat context, and every documentation passage an explanation may cite, quoted with its document path and section. Plain text and tables.
4. One question field with an **Ask** button and a few context-appropriate suggested questions. A suggestion fills the field; it does not send.
5. The answer state with citation links that resolve to source cards on the page.
6. A verdict selector for **Pass**, **Fail**, and **Unreviewed**, an explicit **Save** button, the current saved reason where applicable, and the reading's history.

### Interaction rules

- A loading or failed request does not establish a new reading or answer state.
- An asynchronous result is applied only if it belongs to the latest relevant request. Changing the reading clears its question and answer state; an old response never appears under a different reading.
- While a save is pending, competing saves and scenario navigation are disabled.
- A failed save keeps the selected verdict for retry and shows an actionable error.
- A successful save refreshes the saved verdict, reason, and history from the server.
- Changing scenarios or leaving the page with an unsaved verdict choice asks first. Leaving the page while a save is in flight also asks first. Asking a question does not discard the choice.

## HTTP surface

| Operation | Behavior |
| --- | --- |
| `GET /_/health` | Reports whether the server can read its database, the number of imports it holds (`imports`, 1 after a correct setup), and the configuration fingerprint. |
| `GET /api/scenarios` | The three scenario labels and their resolved reading IDs. No filesystem paths. |
| `GET /api/readings/:id` | Reading detail, supporting facts, advisory, results, saved verdict and reason, repeat context, and history. |
| `POST /api/readings/:id/explanations` | Body `{question}`. Returns the outcome contract. Never writes review state. |
| `POST /api/reviews` | Body `{targets: [{reading_id}], verdict}` with exactly one target. Saves the explicit human verdict. |
| Static | The built UI. |

Unknown `/api/` paths return the JSON `not_found` envelope, never the frontend HTML. The API keeps the request-size limit, strict object decoding, rejection of duplicate and unknown body fields, the error envelope `{error, message}`, missing-reading handling, and generic server-error responses. Causes are logged server-side without credentials or internal errors in responses.

## Configuration and scripts

| Variable | Behavior |
| --- | --- |
| `GEOLINEAI_DB_PATH` | SQLite database path. Default `./var/geolineai.db` relative to the repository root. |
| `GEOLINEAI_HTTP_PORT` | Local port. Default `18080`. Fails clearly when unavailable. |
| `GEOLINEAI_OPENROUTER_API_KEY` | Optional provider key. Empty means explanations return `unavailable` with reason `no_key`; inspection and review still work. |

The server binds to `127.0.0.1`. Provider keys stay server-side. `.env` and `var/` are git-ignored; `.env.example` holds empty placeholders only. These three are the only configuration variables.

Scripts, run from the repository root:

- `scripts/setup.sh` loads `.env` when present, as `scripts/start.sh` does, so both use the same database. It installs dependencies, builds the app, and imports `data/line-1.csv` when the database file does not exist yet. An existing database is opened, not reimported; a database with a different schema is refused with a clear message.
- `scripts/start.sh` loads `.env` when present and serves the built frontend and backend. It never resets or reimports data.
- `scripts/verify.sh` builds, runs the automated checks, then exercises the user journey over HTTP against a fresh temporary database on an unused port, and cleans up only what it created. It does not load `.env`.
- `geolineai import <file>` and `geolineai scenarios` are setup tooling that `scripts/setup.sh` and `scripts/verify.sh` call; they are not a product interface, and the running app offers no import of any kind.
- `scripts/recreate-db.sh` explicitly moves a database and its sidecar files aside, to the trash when available, so the next `scripts/setup.sh` creates a new one at the same path and imports the line. It is never called by the other scripts.

A fresh local run uses either `scripts/recreate-db.sh` followed by `scripts/setup.sh`, or a new `GEOLINEAI_DB_PATH` with `scripts/setup.sh`.

## Acceptance criteria

### Data and evidence

- A fresh setup imports `data/line-1.csv` once and exposes exactly three resolvable scenarios that satisfy their selection rules.
- Criterion results, repeat facts, and line-context facts match the documented dataset facts, pinned by an acceptance test.
- Running setup again does not change counts, duplicate readings, or erase reviews.
- A missing or ambiguous scenario identity fails the import clearly.

### Explanations

Exercised through the real HTTP flow with scripted models from test helpers:

- A supported answer is shown with resolvable citations.
- An unsupported number, an invalid citation, and a verdict recommendation each cause withholding.
- One failing sentence withholds the whole answer.
- A valid unanswerable response is distinct from malformed JSON, missing required fields, and invalid model results, which are `unavailable` with reason `invalid_response`.
- A missing key and a provider failure produce `unavailable` without breaking inspection or saves.
- Asking, refusing, withholding, and failing leave every verdict and history count unchanged.
- Adapter tests cover provider request shapes, parsing, configured retries, and exhausted failure, using a local test server.

### Reviews

- A save affects exactly the requested reading and appends the correct history.
- Pass and Fail get the correct server-built reason; Unreviewed gets none.
- An unchanged save creates no action.
- Missing targets, multiple targets, invalid verdicts, invalid IDs, malformed requests, and database failures write nothing.
- Reload shows the saved verdict and history. A failed save keeps the unsaved choice for retry.
- Later saves append history rather than rewriting it.

### Rendered application

Verified in a real browser against isolated state, with deterministic model behavior supplied by a flag-gated test harness:

- All three scenarios can be inspected.
- Sources are readable and citation links work.
- The shown, withheld, unanswerable, and unavailable presentations are correct.
- Superseded responses never appear under a newly selected reading.
- Only a human Save changes the saved verdict; save-pending and failure behavior follow the interaction rules.
- Keyboard use and narrow layouts work; out-of-scope features are absent.

A live provider run is reported separately from the deterministic checks and is not required for delivery.

### Repository

- The repository builds and runs on its own, with no references to paths outside it.
- No secrets, databases, generated binaries, or dependency directories are tracked.
- Unknown and out-of-scope routes return not found.
